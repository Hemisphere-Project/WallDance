# Subsystem map — camera-recording

*Code-only reading of 2026-11-18 (branch `remote-ops` @ d2ecfde) by an independent reader with no docs or hub context. A description of what the code does, not a design intent. Findings for this subsystem: [findings-blind.md](../findings-blind.md).*

## Purpose

Get frames into the pipeline and takes onto disk. Live: an IDS mono USB3 camera through ids_peak (GenTL) on a background thread, handed to the main loop as a newest-only frame (GPU tensor on the hot path), with exposure/gain/crop control, stall diagnostics and a reconnect state machine. Fallback: any OpenCV device through a threaded cv2.VideoCapture wrapper. Recording: every raw camera frame of a take goes to one of 9 project slots (FFV1 .avi by default) with a .meta provenance sidecar and a 1 Hz camera telemetry log. Playback: a slot take (or an imported external video) is decoded on a pacing thread and fed to the same main loop in place of the camera; it is the surface on which tuning and review happen.

## Architecture

camera/ids_camera.py holds IDSCamera (device, datastream, node map, IDSAcquisition thread, newest-only slot under _frame_lock, stall/frame-id counters, class-level library refcount) and UnifiedCamera (facade that builds a NEW IDSCamera per open, or a CameraManager for OpenCV sources). camera/camera_manager.py: CameraManager = cv2.VideoCapture + CameraCapture thread; in the app a second CameraManager instance (app.camera) is never the device, only the state bag (state.is_open/source/width/height) every controller reads. runtime/camera_controller.py: CameraController owns retry/backoff, the 2.5 s IDS silence watchdog, source refresh, and the ids_ratio/gain/exposure cache re-applied after each open. core/video_recorder.py: VideoRecorder (LIVE/RECORDING/PLAYING state, slot listing, playback decoder thread + one-frame handoff buffer) and _RecordingJob (300-frame queue, RecordingEncoder thread, .meta/.camlog sidecars). core/video_import.py: pure functions copy/transcode a file into a slot. runtime/recording_controller.py: RecordingController wires GUI/remote commands to recorder + camera through narrow ports (RecordingCameraPort etc., adapters in app.py:415-502), queues decoder-thread events for the main loop, runs the import worker. runtime/main_loop.py _tick_acquire is the only consumer and drives reconnects.

## Data flow

Live IDS: WaitForFinishedBuffer -> BufferToImage -> numpy copy -> QueueBuffer (finally) -> _unpack_raw (second copy) -> optional mirror/rotate -> _latest_frame under lock (previous unread frame counted in dropped_frames). If a recording callback is set, the same thread does GRAY2BGR and calls it. Main loop: read_gpu() takes the newest mono8, copies it into a reused pinned buffer, uploads on a dedicated CUDA stream (then synchronizes), expands to (1,3,H,W) float, and also builds a CPU BGR copy (_cached_cpu_bgr) used for preview, the motion feed (which extracts one channel again) and _last_raw_frame. That tensor enters FrameProcessor.process_gpu_direct. OpenCV live and all playback use read()/read_frame() -> BGR numpy -> FrameProcessor.process (upload inside the GPU pipeline); the two entry points converge after upload. Recording: callback -> VideoRecorder.write_frame -> frame.copy() into Queue(300) -> encoder thread -> cv2.VideoWriter; on stop a sentinel drains the queue, then .meta is written. Playback: decoder thread reads the file, sleeps to actual_fps/speed, waits until the previous frame is consumed (no drops), publishes one frame; loop/restart events are queued for the main loop, which resets the tracker and opens a new session folder. Import: validate -> probe -> copy or MJPG transcode to a temp name -> .meta -> atomic rename.

## Threading and state

Threads: main loop (all GenICam control writes, reopen, crop reconfigure, camlog sampling, playback step/seek, UI); IDSAcquisition (frames, stall tracking, recording callback); CameraCapture (OpenCV); RecordingEncoder per take plus a throwaway thread that posts the stop sentinel; playback decoder; VideoImport worker; OpsReadiness. Shared state: IDS newest-frame slot under _frame_lock, each frame a fresh array so no aliasing with the datastream buffers; the pinned upload buffer is main-thread only and synchronized before use. Recorder handoff buffer under _frame_lock, but the cv2.VideoCapture reader itself is touched by both the decoder thread and main-thread next_frame/prev_frame/seek_frame with no lock. Flags (_acquire_running, _playback_running, _frame_new, _frame_callback) are plain attributes relying on the GIL. Library lifetime is a class-level refcount: the only camera's close drops it to 0 and closes the whole IDS peak library; the next open re-initializes it. State is duplicated: UnifiedCamera.is_open/width/height versus app.camera.state.* (kept in sync by hand in CameraController), and ids_exposure_auto/ids_gain_auto exist only once a callback has set them. Clocks: perf_counter (IDS stamps, stall clock, retry), time.time (playback pacing, loop diagnostics), monotonic (encoder, camlog); the device timestamp is read for diagnostics only.

## Failure handling

IDS: WaitForFinishedBuffer timeout (5 frame periods, 150-500 ms) is retried forever and logged every 2 s; 100 consecutive non-timeout errors set _acquire_error and end the thread. The main loop then sees has_error(), or read() returning (False, None), or CameraController._ids_stream_timed_out() (no acquired frame for 2.5 s), and in every case closes the camera, waits 0.5 s and reopens synchronously on the main thread; failed opens back off 1 s x1.5 up to 5 s, forever. Between frames the D34 stall clock (threshold 3 periods, cap 5 s) keeps OSC alive and pauses hold clocks; any reconnect path discards it. Camera absent at startup: same retry loop; replug is picked up by the next attempt. OpenCV: grab/retrieve failure sets _capture_error and takes the same reconnect path, but there is no silence watchdog. Reopen after model load / project-switch errors uses _open_camera directly, which schedules no retry. Recorder: queue full drops frames (counted, printed); a writer that fails to open or a write exception sets job.error and is printed and stored in .meta only; no free-space check. Playback: unreadable file or first frame returns to LIVE; decoder exit makes the main loop go live and restart acquisition. Import: every failure is an operator-readable VideoImportError, temp and .meta are removed.

## Tunables

About 20 named constants in core/config.py: CAMERA_INDEX/WIDTH/HEIGHT/FPS (0, 1920x1080, 30), IDS_MAX_FPS 20, IDS_AUTO_EXPOSURE_LIMIT_US 45000, IDS_CROP_PIXELS 1528*1528, IDS_RATIO 1.0, IDS_USER_SET 'UserSet1', IDS_USE_GPU_DIRECT, CAMERA_STALL_HOLD/PERIODS 3/MAX_S 5 s, RECORDING_CODEC 'FFV1', RECORDING_QUALITY 100, RECORDING_SLOTS 9, RECORDING_GB_PER_HOUR, RECORDING_CAMLOG_INTERVAL_S 1 s, IMPORT_TRANSCODE_CODEC/QUALITY (MJPG/98), OPS_DISK_WARN/FAIL 60/10 GB, OPS_CAMERA_DOWN_ALERT_S 15 s. Roughly 35 more are literals in the code: reopen watchdog 2.5 s, retry backoff 1 s x1.5 max 5 s and reconnect delay 0.5 s (camera_controller.py:73-77, main_loop.py:683-728), IDS stall log threshold 0.4 s, buffer_count 16, wait timeout clamp 150-500 ms, 100-error limit, exposure floor 15 fps / warning 20 fps, fallback exposure 10000 us / gain 6 dB, USB settle sleeps 0.5/0.8/0.3 s, thread joins 1-2 s (ids_camera.py); OpenCV probe range 10, 5 flush grabs, 500 ms first-frame wait (camera_manager.py); queue 300 frames, legacy fps cap 20, finalize waits 15 s / 60 s (video_recorder.py); COPY_CHUNK 8 MiB, DISK_MARGIN 512 MiB, probe after 50 frames, default 25 fps (video_import.py). Per-project keys: camera_source, ids_ratio, ids_gain_db (dB), ids_exposure_us, input_mirror/rotation, camera_stall_hold. Auto exposure/gain flags are not persisted. Seven independent notions of 'stall' exist: 0.15 s, 0.25 s (two), 0.4 s, 2.5 s, 5 s, 15 s.

## Interfaces with neighbours

Pipeline: the camera gives no timestamps, so the output stage clocks on wall time at processing and the tracker counts frames; D34 has to reconstruct silence from main-loop polls. main_loop._camera_period_s uses config constants (20 fps), not the camera's actual rate, which drops to 15 fps when manual exposure is set above 50 ms (the clamp allows 66.7 ms, ids_camera.py:115-135). GPU pipeline: live (process_gpu_tensor) and playback/replay (process) are duplicated bodies. Shared array: get_last_cpu_frame() returns one BGR array that becomes the preview source, the motion worker's input, app._last_raw_frame (plate capture, exposure servo, light ratio) and the STANDBY display frame; when preview size equals source size the preview draws on it in place (main_loop.py:981-982), which would burn overlays into those consumers. Ops monitor: camera health is only is_open + reconnecting; stall counts, stream diagnostics and recorder errors feed no alert. Calibration: CameraController caches the requested exposure/gain, not the node-clamped values; playback_camera corrects gain from the node snapshot but takes exposure from the config. Remote API: StartRecordingSlot reports success from recorder state alone, with or without frames arriving. Logging: every playback loop opens a new session folder and calls os.symlink for 'latest', which fails without symlink privilege on Windows and prints each loop (recording_controller.py:224-233). Config/model controllers treat app.camera (the legacy CameraManager) as the device.

## Strengths

- IDS buffer lifetime is disciplined: the datastream buffer is held only for one memcpy and requeued in a finally block (ids_camera.py:1178-1183); every frame handed out is a fresh array, so the next frame can never overwrite one the pipeline still holds. dropped_frames is explicitly defined as 'app slower than camera', separate from transport losses.
- Stall forensics are well thought out: camera frame-id step and device-timestamp delta classify a stall as camera-silent versus lost-in-transfer, GenTL stream counter deltas and pool state are captured per stall, and the last stalls ride into camlog/.meta (ids_camera.py:189-224, 1307-1378), with fake-based tests (test_ids_stream_diag.py).
- Gain units: dB in the app, the node's own unit detected via Unit(), clamped to the real node range and read back (ids_camera.py:146-186, 1683-1699); playback_camera corrects takes recorded under the old bug (video_recorder.py:311-337).
- Recording provenance is unusually complete: lossless FFV1 default, raw pre-transform frames, node snapshot at start and stop, full config, app version, rig sheet, input transform, 1 Hz camlog, frames queued/dropped/written, and a sentinel-based drain so the tail is never lost (video_recorder.py:79-215). The writer is created on the encoder thread and stop never blocks the GUI.
- video_import.py is careful: probe before accepting, temp name that can never be listed as a slot, .meta written before an atomic rename, free-space check before and projected during a transcode, stale-temp cleanup, clock-skew-safe 'newest' stamp, operator-readable errors, STANDBY gating; all tested.
- Playback is lossless by construction (decoder waits for consumption, video_recorder.py:582-595) and decoder-thread events are queued so tracker state is only mutated on the main thread (recording_controller.py:162-191).
- Pixel parity was reasoned about: the IDS mono path takes one channel directly because it is bit-identical to BGR2GRAY of an R==G==B frame (pipeline.py:1742-1748), and FFV1 takes decode to exactly what the camera delivered.
- The read contract (True, None) = open but no new frame versus (False, None) = error is consistent across IDS, OpenCV and the main loop, and an acquisition thread that died while the camera is still 'open' is funnelled into the reconnect path (main_loop.py:671-684).
- Every reopen uses the project's crop ratio, with a regression test for the field incident that motivated it (camera_controller.py:277, 400-409; test_camera_reopen_ratio.py).

## Questions the reader could not answer from code

- Has a stall longer than 2.5 s been seen in the field, and how long does a full IDS reopen take on the show laptop? Together they decide how bad the watchdog/stall-bridge conflict is in practice.
- Is the reopen after playback-to-LIVE intended (because AcquisitionStart fails with GCWritePort -1001) or an accident of the stale timestamp? Is the -1001 failure understood?
- Do camlogs from show nights show dropped_frames climbing, i.e. does the live loop ever fall behind 20 fps? If yes, playback is systematically kinder than live.
- On the show laptop, does FFV1 at 2.3 MP keep up with 20 fps while the media server runs? Any .meta with frames_dropped > 0 or actual_fps clearly below the camera rate?
- Which is the reference for tuning decisions: in-app playback (wall clock, speed control) or the offline replay (frame/fps clock)?
- Is auto exposure / auto gain ever meant to run during a show? The flags are not saved with the project and every project load forces manual.
- What does UserSet1 contain (gamma, black level, binning, gain selector, throughput limit), and is a spare camera body guaranteed to carry the same set? Nothing checks it at open.
- Which node really caps auto exposure on this camera? The setter tries three names (ids_camera.py:795-797), the provenance snapshot reads a fourth (1791), and the fallback assumes writing ExposureTime under AE acts as a cap.
- Can more than one IDS camera be connected? open() takes the first openable device; there is no serial pinning per project.
- Is the OpenCV path a developer convenience only, or the expected field fallback if the IDS dies mid-show?
- Is the stall root cause still open? The code carries several hypotheses (PCIe contention and a dedicated CUDA stream, throughput limit, buffer starvation, Mono8) while config.py still reports 0.7-2.9 stalls per minute at landscape crops.
